    How it works

    What is WebAssembly (WASM)?

    A compact binary format that browsers run at near-native speed. It lets code written in C, C++ or Rust run in a web page, which is how GMP and Python run here.

    What are GMP and MPFR?

    GMP is the standard C library for very large integers. It switches to faster multiplication algorithms (Karatsuba, Toom-Cook, FFT) as numbers grow. MPFR adds high-precision floating point on top of GMP.

    What are Pyodide and gmpy2?

    Pyodide is the standard Python interpreter (CPython) compiled to WebAssembly. gmpy2 is a Python library that gives Python access to GMP.

    What is a BigInt?

    JavaScript’s built-in integer type with no size limit, written like 123n.

    What’s the difference between BigInt and float mode?

    BigInt mode uses whole numbers with no size limit in every method (JavaScript’s BigInt, Python’s int, GMP’s mpz), so F(n) comes out exact, every digit. Those numbers grow with n: F(1,000,000) is 694,241 bits, and every step works on numbers that big.

    Float mode uses floating-point numbers with a fixed precision of 64 significant digits in every method: decimal.js in JavaScript, Python’s decimal module, and MPFR at 213 bits (called directly or through gmpy2). F(n) is stored as 64 digits and an exponent, like 1.953… × 10^208,987, so every step costs about the same at any n. Binet’s formula, φⁿ/√5, needs fractions, so it is only in float mode.

    Why 64 digits, and how accurate are the floats?

    JavaScript’s ordinary numbers (float64) keep only about 16 digits, are exact only up to F(78), and overflow past F(1,476). Float mode uses libraries that can be set to any precision, all set to 64 digits.

    Each rounding error is tiny, but every step multiplies the errors so far, so a method loses roughly one digit each time n grows tenfold. Binet’s formula loses two or three more, because the error in φ is raised to the n-th power too. Measured: while F(n) fits in 64 digits (up to F(307)), the other methods are exact, and Binet’s formula is exact up to about F(250); at F(10⁹) the methods have 54 to 58 correct digits. So 64 working digits leave room for the 50 that are checked. The page compares every result with Binet’s formula computed with 128 digits; if a method falls below 50, its card says so.

    Why do some floats overflow?

    A float stores an exponent, and the exponent has a limit. MPFR’s is 2^1,073,741,823 (about 10^323,228,496), which fast doubling passes at F(1,546,639,296). Binet’s formula overflows two steps earlier, because φⁿ is √5 times bigger than F(n). Python’s decimal allows up to 10^425,000,000 in a 32-bit build like Pyodide, passed at F(2,033,613,092). decimal.js allows 10^9,000,000,000,000,000, far beyond any n here.

    Why doesn’t the page freeze?

    Each method runs in its own Web Worker, a background thread. The page stays responsive, several methods can use separate CPU cores, and Cancel stops a run instantly.

    Why do the three fast doubling versions differ so much?

    They run the same steps; what differs is how each one multiplies huge numbers. Python’s int stops at Karatsuba, JavaScript’s BigInt (in Chrome) has faster algorithms, and GMP is the most heavily tuned.

    Why does Firefox say “BigInt is too large to allocate”?

    Every browser has its own BigInt code, with its own size limit. Firefox and Safari stop at 1,048,576 bits (about 315,000 digits), so in Firefox the JavaScript methods reach F(1,510,299) and no further. Chrome and Edge allow 1,024 times more, enough for about F(1,500,000,000). The WASM methods don’t have this limit: GMP and Python bring their own big-number code, which is the same in every browser and limited only by memory.

    Does the browser change the speed?

    For BigInt, by a lot. Chrome’s JavaScript engine (V8) multiplies huge numbers with Karatsuba, Toom-Cook and FFT, and turns them into decimal digits with a fast divide-and-conquer method. Firefox still uses the schoolbook methods, whose cost grows with the square of the size. The same code on the same computer:

    GMP barely changes, because both browsers run the very same compiled code. The time estimates on this page were measured in Chrome, so in Firefox the BigInt methods take longer than predicted (the page adjusts after a run). WebKit, Safari’s engine, added the fast multiplication algorithms in autumn 2026, but kept the 1,048,576-bit limit.

    Can even ordinary math differ between browsers?

    Yes. The JavaScript standard lets ** and Math.pow be approximate. φ⁴, from Binet’s formula, is ((1 + Math.sqrt(5)) / 2) ** 4: Chrome gives 6.854101966249686, the correctly rounded answer, while Firefox computes it as (φ·φ)·(φ·φ) and gets 6.854101966249685, one bit lower. WASM doesn’t leave that choice to the browser: its arithmetic must round exactly as the IEEE 754 standard says, and functions like pow are compiled into the module, so the same WASM code gives the same bits everywhere.

    Why is gmpy2 slower than mpz_fib_ui?

    Both call the same GMP function, but from different builds of GMP. gmp-wasm’s build is optimized and tuned for WebAssembly; Pyodide’s is built without GMP’s usual optimization flags.

    Why are only the first and last digits shown?

    The numbers are usually too big to show: F(1,000,000) alone has 208,988 digits.

    Runs methods even when they’re expected to take over 2 minutes or about 1.5 GB of memory. This can take hours, use gigabytes of RAM, and freeze or crash your browser or slow down your computer.
